# 常见开发操作教程

本文面向第一次参与本项目的成员，说明新建页面、复用 UI、新建表单、维护状态机和补充演示数据时应如何操作。

开始前先完成三件事：更新 `main`、创建任务分支、确认自己负责的模块。完整 Git 流程见 [README](../README.md) 和 [新手交接清单](新手交接清单.md)。

## 一、先判断应该修改哪里

| 需求 | 首选修改位置 | 不要直接修改 |
| --- | --- | --- |
| 新建业务页面 | `src/modules/<一级模块>/` | 不要继续往 `app.js` 添加页面 |
| 投诉管理状态/操作权限 | `data/complaint-permission-rules.json` | 按客户 Excel 转写，保留 `sourceRow` 方便追溯 |
| 导航、页面名称、角色可见范围 | `src/core/app-config.js` | 不要在多个页面分别维护权限 |
| 页面专用样式 | 模块目录内的 `module.css` | 不要把专用样式写成全局选择器 |
| 共享按钮、表格、卡片样式 | 先复用 `ui/css/xib-components.css` | 不要复制一套相似组件 |
| 图标和图片 | `ui/assets/` 或业务模块自己的资源目录 | 不要使用不稳定的网络图片地址 |
| 主工单表单字段 | `data/forms/main-work-orders.json` | 不要直接修改 `data/form-schema.json` |
| 子流程与整改字段 | `data/forms/subprocesses.json` | 不要把主单字段混入子流程文件 |
| 工作流状态和流转 | `data/workflow-schema.json` | 不要只改按钮文案或列表状态 |
| 状态标签颜色 | `data/status-tag-config.json` | 不要在页面内为同一状态重复写颜色 |
| 演示记录 | `data/seed-data.json` | 不要向仓库提交真实客户数据 |
| 统计分析页面 | `statistics-module.source.jsx` | 不要修改 `statistics-module.js` 和 `statistics-module.css` |

无法确定位置时，先让 Codex 阅读 `AGENTS.md`、本教程和目标模块 README，再让它只做检查和规划。

## 二、目前已有的开发框架

本项目暂时不是 Vue、React 单页应用，而是一个保留离线打开能力的渐进式模块系统。

页面加载顺序如下：

```text
index.html
  → 运行时数据
  → src/core/app-config.js
  → src/core/module-registry.js
  → src/modules/*
  → app.js 兼容层
```

需要认识四个部分：

1. `app-config.js`：管理导航、页面名称、角色与路由权限。
2. `module-registry.js`：把路由交给对应模块渲染和处理动作。
3. `src/modules/`：新页面和业务功能的主要开发位置。
4. `app.js`：迁移中的旧代码，只用于兼容和提供少量共享接口，不应继续增加新功能。

模块可以使用三个入口：

- `render(page, context)`：返回当前页面的 HTML。
- `afterRender(root, page, context)`：在页面插入后绑定模块内交互。
- `handleAction(action, payload, context)`：处理带 `data-action` 的操作。

`context` 当前提供页面标题、图标、提示、导航、状态标签、筛选、分页和弹窗等能力。优先使用这些公开能力，不要读取 `app.js` 内部变量。

技术规则详见 [模块开发指南](MODULE-GUIDE.md)。

## 三、新建页面

### 第 1 步：确认模块和路由

先在 [模块分工](模块分工.md) 中确认一级模块。路由使用英文小写和连字符，例如：

```text
education-course-list
notification-template-list
```

不要使用中文、空格，也不要重复已有路由。

### 第 2 步：建立模块文件

小页面可以先使用以下结构：

```text
src/modules/education/
├─ index.js
├─ module.css
└─ README.md
```

页面较大时再拆成 `data.js`、`views.js`、`events.js` 和 `state.js`。不要为了“看起来专业”提前建立大量空文件。

### 第 3 步：注册页面

```js
window.XIBModuleRegistry.register({
  name: "education",
  routes: ["education-course-list"],
  render(page, context) {
    return `<section class="page xib-module-education" data-module="education">
      ${context.pageHeader("课程管理", "维护宣传教育课程")}
      <div class="panel ds-card app-card">页面内容</div>
    </section>`;
  },
  handleAction(action, payload, context) {
    if (action !== "education-create-course") return false;
    context.toast("已创建演示课程");
    return true;
  }
});
```

模块名称、根 class 和 action 都应带稳定的模块前缀。

### 第 4 步：加入导航和加载顺序

1. 在 `src/core/app-config.js` 中增加页面、导航和允许访问的角色。
2. 在 `index.html` 中加载模块脚本；必须放在 `module-registry.js` 后、`app.js` 前。
3. 在 `package.json` 的 `check:syntax` 中加入新的 JavaScript 源文件。

### 第 5 步：补充测试

至少检查：页面能进入、关键文字存在、主要按钮能工作、离开再返回不会重复绑定事件、允许的角色可以访问。

## 四、复用 UI 组件

### 复用顺序

1. 先找项目中功能最相似的页面。
2. 复用已有 class 和 `context` 能力。
3. 模块有特殊差异时，写入自己的 `module.css`。
4. 只有三个以上模块都需要时，才考虑增加共享组件。

常用资源：

| 用途 | 推荐方式 |
| --- | --- |
| 页面标题 | `context.pageHeader(title, description, actions)` |
| 主要按钮 | `btn xib-btn xib-btn--primary` |
| 次要按钮 | `btn xib-btn xib-btn--secondary` |
| 表格 | `table ds-table`，外层使用 `table-wrap` |
| 卡片或内容区 | `panel`、`ds-card`、`app-card` |
| 状态 | `context.statusTag(status)` |
| 图标 | `context.icon(name)`；没有对应名称时再查看 `ui/assets/` |
| 提示 | `context.toast(message)` |
| 弹窗 | `context.openModal(...)` |
| 分页 | `context.renderPagination(total)` |

共享样式由 `index.html` 自动加载，模块不要再次引入 `ui/css/xib-components.css`。

页面专用 CSS 必须从模块根开始，例如：

```css
.xib-module-education .course-grid {
  display: grid;
  gap: 12px;
}
```

不要新增下面这类未限定范围的规则：

```css
.panel { /* 错误：会影响全部模块 */ }
button { /* 错误：会影响全部按钮 */ }
```

修改共享 UI 文件前，应单独说明影响范围，并检查至少三个代表页面。新手第一次任务不建议修改共享 UI。

## 五、新建或修改表单

### 第 1 步：确认表单类型

先确认是以下哪一种：

- 主工单录入或处理字段：修改 `data/forms/main-work-orders.json`。
- 子流程或溯源整改字段：修改 `data/forms/subprocesses.json`。
- 表单共享元信息或控件中文名：修改 `data/forms/shared.json`。
- 某个独立模块的简单筛选或弹窗表单：可以放在模块内。
- 多模块共同使用的新业务表单：先定义共享 schema 或明确的数据契约，不要复制多份。

### 第 2 步：修改字段源文件

在对应的 `data/forms/*.json` 中维护分组和字段。`data/form-schema.json` 是自动合并的兼容文件，不要直接编辑。常见属性包括：

```json
{
  "name": "客户姓名",
  "type": "text",
  "required": true,
  "placeholder": "请输入客户姓名"
}
```

新增字段时至少确认：

1. 字段名称是否唯一且稳定。
2. 类型是否已有渲染支持。
3. 哪些工单类型可见。
4. 是否必填、默认值和校验范围。
5. 提交后保存到哪个阶段或数据对象。
6. 详情页、审批页和导出是否也要展示。

不要仅让输入框显示出来，却忘记保存、回显和校验。

### 第 3 步：生成运行时数据

修改 `data/` 后执行：

```powershell
npm run build
npm run check:generated
npm run verify
```

`data/form-schema.json` 与 `data/prototype-data.runtime.js` 都是生成文件，不要手工编辑，也不要手工解决它们的冲突。应先解决 `data/forms/` 中的源文件，再重新生成。主工单和子流程可以由不同维护人并行修改；同一文件需要多人维护时，继续使用短分支和小 PR，不要为每个字段新建文件。

## 六、维护状态机

状态机包含“当前状态 + 事件 → 下一个状态”。不要把它理解成页面上的状态文字列表。

例如：

```json
"claim": {
  "待处理": "处理中"
}
```

表示当前为“待处理”时执行 `claim`，状态变为“处理中”。

### 修改步骤

1. 在 `data/workflow-schema.json` 中找到 `ticket`、`subprocess` 或 `rectification`。
2. 如有新状态，先加入该状态机的 `statuses`。
3. 在 `transitions` 中增加或修改事件允许的起始状态和目标状态。
4. 检查按钮显示条件、角色权限和审批规则是否需要同步。
5. 在 `data/status-tag-config.json` 中确认新状态的颜色。
6. 在 `data/seed-data.json` 中准备至少一条能走到该状态的假数据。
7. 补充合法流转和非法流转测试。
8. 运行构建和完整验证。

当前主工单流程约定：投诉单由处理员填写“是否会签”；选择“是”时，“会签机构”为条件必填的机构/部门多选字段，提交后进入“会签中”，会签通过后进入审批；选择“否”时隐藏会签机构并直接进入审批。信访单在处理后进入初审，初审通过后进入审批；其他主工单从处理直接进入审批。`会签中` 只能用于投诉单，审批管理中的“会签”和“初审”共用同一操作列。

关联子流程不要再增加“是否发起某子流程”一类重复字段。统一根据子单编号是否为空判断是否发起，申请状态使用子单状态，子流程结论读取子单的同名结论字段。“关联子流程”和“关联单据”必须调用同一份关联数据规则。管理页面只展示未办结记录；需要查看全部状态时进入“查询导出”。

导出申请按照“草稿、待审批、审批中、已通过、已驳回”维护状态。工单导出和子流程单导出统一点击“导出”：选择“脱敏导出”时直接导出并写入导出台账；选择“非脱敏导出”时必须勾选敏感字段并提交导出审批。草稿和已驳回的导出申请可继续编辑，待审批可查看、催办、撤回，审批中可查看、催办，已通过可查看、下载。

### 子流程状态矩阵维护

子流程不是一条所有类型共用的直线流程。`data/workflow-schema.json` 中的 `documentStateMachines.subprocess.typeStatusMatrix` 决定每种子流程可以进入哪些状态，`transitions` 只定义合法事件如何改变状态。

修改子流程流转时按以下顺序操作：

1. 先在需求表中确认该类型是否有复核、处理、审批和补录。
2. 修改 `typeStatusMatrix`，不要通过页面里的 `if` 临时跳过节点。
3. 如需新事件，再修改 `transitions`。
4. 同步检查 `data/forms/subprocesses.json` 的 `approval_rules` 与 `supplement_sections`。
5. 在 `data/seed-data.json` 中为新增状态提供样例。
6. 运行 `npm run test:subprocess-contract` 和 `npm run test:supplement`。

撤销投诉、废止申请和投诉校正只有在关联主工单来自客服电话或在线客服时才经过“待复核 → 复核中”。撤销投诉复核通过后直接办结；废止申请和投诉校正复核通过后进入待审批。其他类型按状态矩阵直接进入处理、审批或办结。

### 子流程字段表同步

业务人员提供 Excel 字段表时，先逐行核对页面分区、控件类型、必填、可编辑、来源、字典、联动和备注，再落到 `data/forms/subprocesses.json`。Excel 是评审输入，不是运行时依赖。

- 所有类型共有的基础字段放入 `base_field_rules.common_fields`。
- 只属于某类子单的基础字段放入 `base_field_rules.type_fields.<类型>`。
- 创建和处理业务字段放入 `field_sections.<类型>`。
- 处理阶段可编辑分区写入 `process_section_titles.<类型>`。
- 审批通过后才填写的字段放入 `supplement_sections.<类型>`。
- 下拉联动使用 `optionsBy`，只读自动回填使用 `valueMap`，不要在页面中复制字典判断。

字段修改必须同时检查新建页、处理页、审批页只读回显、补录页、详情页和样例数据。`data/form-schema.json` 与 `data/prototype-data.runtime.js` 由构建命令生成，不手工编辑。

状态机修改必须回答四个问题：

- 谁可以触发？
- 从什么状态触发？
- 触发后到什么状态？
- 失败、退回或撤销时到哪里？

不要只修改 `statuses` 而不修改 `transitions`；不要只改按钮动作而绕过 schema；不要把浏览器前端权限当成生产系统权限。

如现有浏览器保存数据的结构发生不兼容变化，还要评估 localStorage 版本和旧数据迁移。不要在没有迁移方案时直接改变已保存对象的含义。

## 七、补充演示数据

演示数据统一使用虚构内容，并尽量覆盖：

- 列表空状态和有数据状态；
- 正常、待处理、退回、失败等关键状态；
- 详情页关联关系；
- 不同角色可见的数据；
- 新增状态机的主要路径。

修改 `data/seed-data.json` 后同样需要运行构建。不要把仅存在于某位同事浏览器 localStorage 中的数据当成项目数据；其他成员和 Netlify 线上原型看不到它。

## 八、增加跨模块能力

如果一个需求要从 A 模块打开 B 模块，不要直接查找或修改 B 模块的 DOM 和变量。

正确处理顺序：

1. 先确认是否已有 `context` 接口。
2. 没有时，定义一个职责单一的共享接口。
3. 在 `src/core/`、`src/shared/` 或兼容层实现。
4. 在技术文档中写清参数、返回值和失败行为。
5. 为调用方和被调用方补充测试。

共享接口应单独审查。不要因为“只差一行”就在模块之间建立隐式依赖。

## 九、提交前检查

普通页面修改：

```powershell
npm run verify
git diff --check
```

修改数据、表单、状态机或统计源文件：

```powershell
npm run build
npm run check:generated
npm run verify
git diff --check
```

还要人工检查：

1. 直接双击 `index.html` 是否能运行。
2. 目标角色能否看到并进入页面。
3. 主要操作、错误提示、返回和刷新是否正常。
4. 是否修改了任务范围以外的模块。
5. 新状态或字段是否能保存并回显。

## 维护会签与关联子流程

### 会签信息维护

主工单“处理信息”中的会签配置位于独立的“会签信息”分区。处理员先选择“是否会签”；选择“是”后，通过“会签机构”多选控件从机构树选择机构或部门。机构树源文件是 `data/organization-tree.json`，不要在页面代码中另写一份机构名单。

多人会签样例位于 `data/seed-data.json`：

`documentData.tickets.<工单编号>.fields.countersign.会签明细`

每位会签人一条记录，填写“会签机构、会签人、会签状态、会签结论、会签意见”。审批管理会把这些记录逐行展示；当前会签人的行可以编辑。机构标签必须保留总行或分行前缀，避免不同机构的同名业务部门混淆。全部会签人完成前工单保持“会签中”；全部完成后转为“待审批”；审批人领取后转为“审批中”。

### 关联子流程维护

关联子流程表每个子单独占一行。同一子流程类型有多个子单时，“子流程类型”单元格会自动纵向合并，其他字段仍与具体子单一一对应。操作栏只展示“发起”和“详情”。

六类结论字段统一显示为“字段名称 - 字段值”：撤销投诉、异常投诉、剔除申请、投诉问责、纠纷化解、异议核查。修改子单结论时，应更新对应子单 `documentData.subprocesses.<子单编号>.fields` 中的同名字段：有处理阶段的类型写入 `fields.processing`，无处理阶段的类型写入创建/申请阶段字段，不要在主工单里复制一份结论。

调整子单关联主工单时，需要同步修改：

1. `lists.subprocesses[].relatedTicketId`
2. `documentData.subprocesses.<子单编号>.relatedTicketIds`
3. `documentData.subprocesses.<子单编号>.fields.base.关联工单编号`

修改后运行 `npm run build:data` 和 `npm run verify`。


## 维护子流程补录字段

延长申请、异常投诉和剔除申请在审批通过后进入“待补录”。补录没有独立页签：有处理阶段的子单显示在“处理信息”最后；无处理阶段的子单显示在“基本信息”最后。此阶段其他字段和审批结果均只读，只有补录分区可操作。

字段配置位于 `data/forms/subprocesses.json` 的 `subprocesses.supplement_sections`。新增或调整补录字段时，先修改该配置，再运行 `npm run build:data`。

延长申请的“告知延期时间”和“告知延期方式”不能手填。经办人从上方联系记录选择一条数据后，系统分别读取该记录的联系时间和沟通方式自动回填。异常投诉和剔除申请使用各自独立的结果字典。

修改后至少运行：`npm run test:supplement`、`npm run verify`。
