# 新手同事交接清单

这份清单用于把一个已经划定边界的模块交给第一次参与 GitHub、Codex 或多人协作的同事。新同事不需要先学会全部 Git 命令；需要先学会“不在 `main` 直接开发、一次只改一个模块、检查通过后再合并”。

## 一、负责人交接前准备

负责人在分配任务前完成以下事项：

1. 邀请同事加入私有 GitHub 仓库，并确认对方能够打开仓库和 Actions。
2. 明确同事只能在功能分支开发并提交 PR，不得直接推送 `main`。
3. 在 [模块分工](模块分工.md) 中写清负责人、共同维护人和任务范围。
4. 在 `.github/CODEOWNERS` 的同一条路径后列出全部共同维护人。
5. 使用 [模块任务 Issue 模板](https://github.com/sophia6703/TRS-XIB/issues/new?template=module-task.md) 建立一个只涉及一个模块的任务，写清页面、角色、预期结果和验收步骤。

适合新手的第一项任务应当能在半天到一天内完成，例如调整一个列表字段、补一个筛选条件、完善一个占位页面或修复一个明确的交互。不要把“拆分 `app.js`”“重构统计模块”作为第一次任务。

## 三、新同事第一次操作

### 1. 克隆并打开项目

推荐使用 GitHub Desktop 克隆仓库，然后用 Codex 打开本项目文件夹。首次进入 Codex 后先发送：

```text
请先阅读 README.md、AGENTS.md、docs/模块分工.md，
以及我负责的模块目录内 README.md 和 AGENTS.md。
先不要修改代码。请用中文告诉我：
1. 我可以修改哪些文件；
2. 哪些共享文件不能随意修改；
3. 完成任务前需要运行哪些检查。
```

### 2. 安装并运行

在项目目录执行：

```powershell
npm install
npm run dev
```

浏览器打开 <http://127.0.0.1:8080/>。只做演示时仍可直接双击 `index.html`。

### 3. 更新 main 并创建任务分支

在 GitHub Desktop 中切换到 `main`，点击 **Fetch origin** 和 **Pull origin**，再使用 **New branch** 创建分支。分支示例：

```text
feat/education-course-list
fix/admin-user-filter
refactor/complaint-approval-module
```

不要直接在 `main` 上让 AI 修改代码。

## 四、交给 Codex 的任务模板

```text
我负责 src/modules/education/。
请先阅读仓库规则和该模块说明，只处理“增加课程列表筛选”这个任务。
不要修改 app.js、statistics-module.source.jsx、其他业务模块或生成文件。
先检查现有实现和测试，再实施最小修改。
完成后运行相关聚焦测试和 npm run verify，更新必要的中文成员文档与英文 AI 技术说明。
不要直接合并；先给我说明可见变化、风险和验证结果。
```

如果 Codex 判断必须修改 `src/core/`、`src/shared/`、`styles.css`、`app.js` 或其他模块，应先停止实现并解释原因，由负责人决定是否拆成共享基础能力 PR。

## 五、提交与 PR

新同事完成后至少做到：

1. 在浏览器中按目标角色走一遍主要操作。
2. 直接双击 `index.html`，确认演示入口仍可运行。
3. 执行 `npm run verify`。
4. 在 GitHub Desktop 检查 Changed files，确认没有无关目录和临时文件。
5. 使用英文 Conventional Commit，例如 `feat: add education course filters`。
6. 推送分支并创建中文 PR。
7. 等待 GitHub `verify` 成功。
8. 由模块维护人确认业务表现后 squash merge，禁止跳过失败检查；合并后由仓库负责人确认 Netlify Production Deploy 成功。

PR 正文至少写清：修改目的、模块与路由、可见结果、验证命令、合并后需要检查的线上路径、风险和后续工作。

## 六、同一模块多人维护

同一模块可以有多名维护人，但不要让多人在同一个任务分支上同时让 AI 大范围改写。推荐拆成不同页面或不同能力，每人一个分支和 PR。

例如：

```text
/src/modules/education/ @owner-a @owner-b
```

同一路径的共同维护人写在 CODEOWNERS 同一行。CODEOWNERS 默认只要求其中一名代码所有者批准；如果必须两人批准，还要在 GitHub `main` 的 Ruleset 或 Branch protection 中把 Required approvals 设置为 2。

## 七、负责人审查重点

- PR 是否只修改约定模块。
- 是否新增了另一个模块的 DOM、状态或数据依赖。
- 是否把新业务代码继续塞进 `app.js`。
- 是否直接修改 `*.runtime.js`、`statistics-module.js` 或 `statistics-module.css`。
- 页面、角色权限和直接打开方式是否正常；合并后 Netlify 正式地址是否完成更新。
- PR 的测试结果是否来自真实执行，而不是 AI 推测。

## 八、交接完成标准

当新同事能够独立完成“更新 `main` → 创建分支 → 让 Codex 在模块内修改 → 本地验证 → 推送 PR → 查看 CI → 等待维护人合并”这一轮流程，才算完成交接。

建议第一个 PR 由负责人陪同完成；第二个 PR 开始让同事独立操作，负责人只在模块边界、业务验收和合并阶段介入。
