# 原型结构化数据

本目录中的 JSON 是原型字段、状态机和初始演示数据的唯一配置源。

## 文件

- `forms/main-work-orders.json`：主工单录入与处理字段源。
- `forms/subprocesses.json`：子流程与溯源整改字段源。
- `forms/shared.json`：表单元信息、运行时存储契约和控件中文名。
- `form-schema.json`：由上述三份源文件合并生成的兼容文件，请勿手工修改。
- `workflow-schema.json`：单据状态、状态迁移事件和审批规则。
- `customers.json`：客户主数据，按客户编号维护身份、联系方式、人口属性、居住地、客户经理及合并关系。
- `seed-data.json`：恢复默认数据时使用的列表、完整单据字段、客户快照和流转历史。
- `organization-tree.json`：机构管理使用的扁平机构记录，通过 `parentId` 组成树，`depth` 用于层级筛选。
- `tag-trees.json`：金管/人行/TRS 各类标签树，供级联与字典选择器读取。
- `region-tree.json`：居住地省市区三级树（含香港、澳门特别行政区和台湾省，坚持一个中国原则），省级含“不清楚”选项；《国家地区》字典由 `forms/main-work-orders.json` 维护，中华人民共和国置顶，其他国家不包含港澳台。
- `form-fields.csv`：由表单结构展平的人工核对视图，不作为运行时配置源。
- `prototype-data.runtime.js`：由 JSON 自动生成，供浏览器和 `file://` 本地打开使用，请勿手工修改。

## 维护人设置

`.github/CODEOWNERS` 已为三份字段源预留独立规则。增加维护人时，在对应文件规则后追加 GitHub 用户名；同一规则可以列出多人。CODEOWNERS 默认表示其中任意一人批准即可，如果业务要求两人都批准，还需在 GitHub 分支保护规则中提高必需批准数。

## 修改流程

1. 修改对应源 JSON；主工单和子流程字段不要改错文件。
2. 生成字段聚合文件和浏览器运行时文件：

   ```powershell
   node .\tools\sync-prototype-data.js
   ```

3. 校验编号、状态、完整记录、状态机和机构树父子关系：

   ```powershell
   node .\tools\validate-prototype-data.js
   ```

4. 打开 `index.html` 或本地 HTTP 地址检查交互。

## 运行时存储

- 初始数据来自 `seed-data.json`。
- 用户操作保存到当前浏览器的 `localStorage`；当前数据版本对应 `seed-data.json` 中的 `meta.storageVersion`，目前为 `xib-prototype-state-v18`。
- 不同浏览器、设备和访问者互不影响。
- 顶部的“恢复默认数据”会清除运行态并重新读取初始数据。
- 修改了不兼容的数据结构时，提升 `seed-data.json` 中的 `meta.storageVersion`，即可让浏览器使用新的存储键。

## 客户主数据与工单关联

- `customers.json` 是客户查询和客户画像的客户属性唯一来源，字段使用嵌套结构保存，避免页面直接依赖中文表单字段。
- 主工单 `documentData.tickets.<工单编号>.fields.entry["客户编号"]` 是指向客户主数据的关联键；同一工单仍保留建单时的客户字段快照，便于后续对接审计与历史追溯。
- “查看历史工单”和客户画像按客户编号从真实 `lists.tickets` 与 `documentData.tickets` 聚合；历史工单包含该客户全部已办结主工单。投诉统计展示累计以及投诉、信访、建议、表扬四类数量：累计只读，四类工单可筛选历史；投诉路径严格按受理渠道归入“行内投诉、网微投诉、监管投诉”三级显示数量并筛选历史，共 7 个筛选按钮；两组筛选互斥，重复点击当前按钮取消筛选；卡片底部展示已办结工单、四类工单、重复投诉及历史监管投诉结论；近一年窗口仅用于“重复投诉”认定。不维护独立模板，也不复用“关联单据”的再次投诉/子单关系。`舆情单` 已停止使用：表单源不提供创建选项，运行时需过滤遗留舆情样例。
- `mergedIntoCustomerId` 用于历史客户号归并；匿名、资料不完整和单位客户允许部分自然人属性为空，页面必须展示空状态或 `-`，不能伪造默认身份证、手机号和性别。
- 修改客户主数据或工单客户快照后，运行 `npm run build:data`、`npm run test:customer-data` 和相关 UI 测试。

## 完整单据结构

列表信息与表单字段分开保存：

```json
{
  "lists": {
    "tickets": [
      {
        "id": "TS202607230012",
        "type": "投诉单",
        "customer": "陈晓敏",
        "subject": "贷款协商还款",
        "org": "零售金融部",
        "status": "处理中",
        "updatedAt": "2026-07-23 09:32"
      }
    ]
  },
  "documentData": {
    "tickets": {
      "TS202607230012": {
        "id": "TS202607230012",
        "documentType": "投诉单",
        "schemaVersion": "1.1.0",
        "fields": {
          "entry": {},
          "processing": {},
          "review": {},
          "initialApproval": {},
          "countersign": {},
          "approval": {}
        }
      }
    }
  }
}
```

列表用于检索和表格展示，`documentData` 用于详情、编辑、审批和历史工单。增加模拟工单时，两处使用相同的 `id`。

## 机构树结构

机构树采用扁平父子引用，便于后端接口直接返回、按编号快速检索和独立校验：

```json
{
  "id": "0001000110011001",
  "parentId": "000100011001",
  "name": "办公室",
  "depth": 3,
  "typeName": "总行部门"
}
```

运行时根据 `parentId` 建立层级视图；筛选时保留匹配节点的祖先路径。修改后运行同步和校验脚本，不直接编辑 `prototype-data.runtime.js`。

## 客服电话复核与智能派发规则

- `workflow-schema.json` 的 `approvalRules.ticketReviewChannels` 维护按受理渠道进入复核的规则，目前为“客服电话”。客服电话投诉单在创建提交时不弹出短信确认；复核结论为通过时复用原短信确认窗，确认后流转至待处理，并按选择写入短信联系记录。不通过、取消确认或选择不发均不发送。
- `forms/main-work-orders.json` 的“派发部门”通过 `optionsByInstitution.departmentNameIncludes` 筛选“普惠、消费者权益保护”两类直属部门，名称以当前启用机构树为准，不生成机构树中不存在的部门。
- `emptyForSubbranch: true` 表示支行层级的派发部门保持空值、不必填、不可选；切换机构时清除失效的旧部门。此规则只作用于智能派发，转派等其他机构部门控件不受影响。
- “抄送人”在工单创建页和详情页固定展示，为系统只读字段。总行消保或客服中心创建工单、且直接派发至分行普惠部门或支行时，该字段必填，并自动回填目标所属分行消费者权益保护部下全部在职业务员；其他场景显示“-”、不必填。人员取自后台用户主数据，按部门编码、岗位、启用状态和在职状态匹配。
- 子单 `fields.base.抄送人` 为结构化只读字段：撤销投诉取关联主单处理员，投诉校正取关联主单经办员，30 日延长申请取“审批员（总行消保部主管）”。子单详情在“基本信息”页签的创建信息之后、补录信息之前统一展示抄送信息。

## 人行标签与新建单据联动规则

- “客户类型”是 AI 智能打标的前置必填项。自然人使用 A（业务办理渠道）、B（业务类别）、C（投诉/信访原因）标签；非自然人使用 Z、Y、X 标签。切换客户类型时清空已有三项人行标签，避免保留另一客户类型的失效枚举值。
- 新建主单提交后默认进入接收机构的“机构工单池”，状态为“待处理”；处理人领取后转为“处理中”，并进入该处理人的“我的工作台”。需要客服复核的主单仍先进入复核流程。
- 新建子单若未直接指定处理人，则按状态进入对应机构工单池；若规则允许直接处理且已选择处置员，提交后状态为“处理中”，写入所选处置员并进入其“我的工作台”。

## 导出申请结构

- `lists.exportRequests[].exportType` 仅使用“工单、子单、溯源整改单、报表”四项字典；`org` 与 `department` 分别存储申请人所属机构和所属部门。
- 查询导出与审批管理复用导出类型、导出申请状态和申请人归属字段，筛选直接匹配结构化记录，不依赖列表当前展示了哪些列。
