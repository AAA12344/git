# 厦门国际银行消费者权益保护系统交互原型

> 最后更新：2026-08-10<br>
> 项目性质：静态前端交互原型，无真实客户数据、后端、数据库和生产接口。<br>
> GitHub 仓库：<https://github.com/sophia6703/TRS-XIB>

本项目用于共同梳理消费者权益保护系统的页面结构、角色权限、表单字段、审批和流转逻辑。项目正在从单文件原型逐步迁移成可由不同成员、不同 AI 分模块维护的结构。

## 一、快速运行

### 方法 A：直接打开

双击 `index.html` 即可运行。项目保留 `file://` 打开方式，并有自动化回归测试防止后续修改破坏它。

适合：演示、快速查看、不会命令行的同事。

### 方法 B：使用本地服务器（开发时推荐）

首次使用需要安装 Node.js 20 或更高版本，然后在项目目录运行：

```powershell
npm install
npm run dev
```

浏览器打开：<http://127.0.0.1:8080/>

开发完成后运行：

```powershell
npm run verify
```

如果修改了 `data/`、统计模块源码或生成脚本，还要运行：

```powershell
npm run build
npm run check:generated
```

`npm run build` 是本地完整生成命令，需要已安装的 Edge 或 Chrome。Netlify 使用 `npm run build:deploy`：同步普通数据并检查已提交的统计生成产物，不在云端重复启动浏览器。

### 方法 C：在线访问（Netlify）

无需本地安装，直接访问 Netlify 部署的在线原型：

<https://trsxib.netlify.app/>

Netlify 仅使用 `main` 作为生产分支。协作者在功能分支完成修改并提交 PR，由仓库负责人审核；PR 合并到 `main` 后，Netlify 自动部署并更新线上原型。功能分支不会影响正式地址。在线版本同样支持角色切换和“开发测试视图”，适合没有本地环境或需要远程查看的同事。

### 剩余结构迁移量

后台管理现已完成结构迁移。按“一个边界、一个 PR”估算，达到 `app.js` 只保留兼容启动代码的目标，仍约需 **5～10 个聚焦 PR**：投诉管理主流程约 2～5 个，统计分析 / 首页 / 报告中心约 2～4 个，最终共享代码收口约 1 个。这个数字不包含接入真实后端；后端 repository、接口 schema 和契约测试属于后续阶段。

PR 数量不等于平均工时。剩余的工单、子流程和统计源码是当前最大的代码块，应继续由架构维护者先迁出边界，再交给新手成员并行开发。详细顺序见 [迁移路线](docs/MIGRATION-ROADMAP.md) 和 [模块分工](docs/模块分工.md)。

## 四、零基础协作流程

### 第 0 步：任务模块确认

打开 [一级模块分工](docs/模块分工.md)，确认自己只修改一个模块。不要用“顺手”作为理由同时修改别人的模块。

好的任务示例：

- “在宣传教育模块增加课程列表占位页。”
- “修复通知中心列表的筛选重置。”
- “把后台表单配置从 `app.js` 迁到 `src/modules/admin/form-config/`。”

不好的任务示例：

- “顺便统一所有页面样式。”
- “把整个 `app.js` 重写成 React。”
- “同时修改工单、通知和后台管理。”

### 第 1 步：本地 `main` 更新

使用 GitHub Desktop：

1. 打开仓库。
2. 左上角分支选择 `main`。
3. 点击 **Fetch origin**。
4. 如果出现 **Pull origin**，继续点击。

使用命令行：

```powershell
git switch main
git pull --ff-only origin main
```

### 第 2 步：任务分支创建

不要直接在 `main` 上开发。分支名使用英文小写：

```text
feat/education-course-list
fix/notifications-filter-reset
refactor/admin-form-config
docs/onboarding-guide
```

GitHub Desktop 中选择 **Current branch → New branch**；命令行可以运行：

```powershell
git switch -c feat/education-course-list
```

### 第 3 步：Codex 规则与任务输入

在 Codex 中打开整个 `Prototype` 文件夹，而不是只打开某个 HTML。建议使用以下提示词：

```text
请先阅读 AGENTS.md、README.md、docs/ARCHITECTURE.md，
再阅读 src/modules/education/ 下的说明。

目标：在宣传教育模块增加课程列表。
范围：只修改 src/modules/education/ 和必要的测试。
约束：保留 index.html 直接打开方式；不要修改其他一级模块。
完成标准：页面可操作，新增聚焦测试，npm run verify 通过。
先检查和规划，再开始修改。
```

提示词最好包含四项：目标、上下文、约束、完成标准。复杂任务先让 Codex 规划，不要一上来就要求“全部重构”。

### 第 4 步：页面人工检查

AI 说“测试通过”不等于业务正确。至少检查：

1. 直接打开 `index.html` 是否正常。
2. 使用“开发测试 / 开发测试视图”进入目标页面。
3. 主要按钮、标签页、弹窗、筛选和返回操作是否正常。
4. 是否误改了其他模块。
5. 中文文案和页面层级是否符合需求。

### 第 5 步：提交前审查

可以直接说：

```text
请审查当前未提交变更：
1. 是否越过模块边界；
2. 是否破坏已有角色、路由和 file:// 打开方式；
3. 是否需要新增测试或文档；
4. 运行 npm run verify；
5. 不要提交，先把发现告诉我。
```

Codex App 或 CLI 中也可以使用 `/review` 审查未提交变更或相对 `main` 的分支差异。

### 第 6 步：变更提交与推送

commit 使用简短英文 Conventional Commit，方便工具识别：

```text
feat: add education course list
fix: reset notification filters
refactor: extract admin form config module
docs: expand onboarding workflow
```

然后推送分支：

```powershell
git push -u origin feat/education-course-list
```

GitHub Desktop 可直接点击 **Publish branch**。

### 第 7 步：PR 创建

本项目在 GitHub 上，所以统一叫 **PR（Pull Request）**；GitLab 中同类功能叫 **MR（Merge Request）**。

推荐规则：

- PR 标题和正文使用中文，方便中国同事阅读。
- commit 和代码标识符使用英文。
- PR 只解决一个模块或一个共享前置问题。
- UI 变化附截图，并说明合并后需要检查的线上路径。
- 说明影响的路由、角色、测试结果和回滚方式。

示例标题：

```text
【宣传教育】新增课程列表与分类筛选
```

### 第 8 步：自动检查与审查

PR 页面出现绿色检查前不要合并。当前 CI 会检查：

- JavaScript 语法；
- 配置、演示数据和关联关系；
- 生成文件是否最新；
- 浏览器主要流程；
- `index.html` 的 `file://` 直接打开方式。

如果使用 Codex GitHub 代码审查，可以在 PR 评论中输入 `@codex review`；也可以在 Codex 本地使用 `/review`。AI 审查不能替代业务负责人对页面和流程的确认。

### 第 9 步：PR 合并

全部满足后使用 **Squash and merge**。这样一个 PR 在 `main` 上只形成一个清晰提交，初学者更容易回滚和理解历史。

合并后删除远程任务分支，并让其他成员重新更新 `main`。

## 五、多人并行开发规则

1. 一个模块可以配置多名维护人；一个人一次只维护一个任务分支。
2. 一个 PR 默认只涉及一个一级模块。
3. 两个人不要同时编辑 `app.js` 或 `statistics-module.source.jsx`；先把目标路由迁出。
4. 不要跨模块读取 DOM、内部变量或演示数据。
5. 共享功能先做独立的 `src/core/` 或 `src/shared/` PR。
6. 不直接编辑生成文件：`statistics-module.js`、`statistics-module.css`、`data/*.runtime.js`。
7. 不使用强制推送覆盖 `main`，不使用“整文件选 ours/theirs”粗暴解决冲突。
8. CI 失败不合并；测试无法运行时必须在 PR 写明原因。

## 六、冲突处理

先不要点 GitHub Desktop 的“保留全部我的/他的”。把冲突交给 Codex 时这样说：

```text
当前分支和 main 有冲突。
请先解释冲突两边各自想保留的行为，再提出最小解决方案。
不要删除任何一边的功能，不要使用 git reset --hard，不要强制推送。
解决后运行 npm run verify。
```

如果冲突发生在生成文件：先解决源文件，然后运行 `npm run build` 重新生成，不要手工拼生成文件。

## 八、角色和演示数据

顶部“视角”按机构和角色切换。开发和交接演示建议使用“开发测试 / 开发测试视图”，它包含所有页面入口和演示操作。

当前角色视角用于前端开发测试：经办员对应创建页面、处理员对应处理页面、复核员/审批员对应审批管理。正式的用户视角隔离和权限安全控制尚未接入，开发测试视图通过切换角色展示各模块流程。

本项目没有数据库。用户操作写入浏览器 `localStorage`，仅用于单机演示，不支持多人实时同步、真实权限隔离、审计或并发控制。

结构化数据源：

| 内容 | 源文件 |
| --- | --- |
| 主工单字段 | `data/forms/main-work-orders.json` |
| 子流程与整改字段 | `data/forms/subprocesses.json` |
| 表单共享元信息与控件名称 | `data/forms/shared.json` |
| 流程和审批规则 | `data/workflow-schema.json` |
| 状态标签 | `data/status-tag-config.json` |
| 客户主数据 | `data/customers.json` |
| 演示记录及工单客户快照 | `data/seed-data.json` |
| 机构树 | `data/organization-tree.json` |
| 标签树（TRS 渠道/产品/原因/诉求、金管、人行） | `data/tag-trees.json` |
| 居住地省市区树（含港澳台，坚持一个中国原则） | `data/region-tree.json` |
| 投诉管理角色状态/操作权限 | `data/complaint-permission-rules.json` |
| 导航、角色、页面权限 | `src/core/app-config.js` |

`data/form-schema.json` 和 `data/prototype-data.runtime.js` 都是生成文件，不要直接修改；执行 `npm run build:data` 会先合并三份字段源，再生成浏览器运行时数据。主单和子单字段分开维护，同一业务文档的字段保持在同一文件中，避免拆成大量难以追踪的小文件。客户查询、工单创建回填和客户画像统一读取 `data/customers.json`；工单以录入字段中的“客户编号”作为关联键，同时保留建单时的客户快照。“查询并回填”仅负责查询客户主数据并回填当前表单，“查看历史工单”直接按当前表单中的客户身份字段独立查询，二者没有前置依赖。“历史工单”按同一客户编号查询全部已办结主工单；客户画像右侧统一为“投诉统计”卡：累计为不可点击的只读统计；投诉、信访、建议、表扬四类统计可筛选历史工单；下方投诉路径严格按受理渠道分为三级（行内投诉 → 网微投诉 → 监管投诉）并可按等级筛选，因此一共 7 个筛选按钮。类型与等级筛选互斥，重复点击当前按钮取消筛选；卡片底部按真实历史数据展示已办结工单、四类工单、重复投诉及历史监管投诉结论。“重复投诉”仅按“同一客户 + 投诉产品标签中类相同 + 两张投诉工单处于一个自然年内”认定；“关联单据”仅展示当前工单链路内的再次投诉和子单等关联，三者口径不得混用。所有执行查询的列表和弹窗在零结果时统一展示项目空状态，不保留空白表格或旧结果。舆情单已按业务要求下线：运行时过滤遗留舆情记录，创建、筛选和后台表单配置均不得出现“舆情单”。


主工单处理阶段的流程约定：投诉单由处理员必选“是否会签”；选择“是”后还须从机构管理口径中多选“会签机构”，并按“处理 → 会签 → 审批”流转，选择“否”则按“处理 → 审批”流转；信访单按“处理 → 初审 → 审批”流转。审批管理中的“会签”和“初审”共用同一操作列。字段和状态不得只改页面文字，必须同步修改上述结构化数据源并执行完整验证。

主工单状态总顺序为：`草稿 → 待提交 → 待复核 → 复核中 → 待处理 → 处理中 → 会签中 → 待初审 → 初审中 → 待审批 → 审批中 → 已办结/已废止`；投诉、信访、建议、表扬的实际适用状态由 `data/workflow-schema.json` 的 `documentStateMachines.ticket.typeStatusMatrix` 控制。信访单处理后先进入独立的“待初审/初审中”，通过后才进入“待审批/审批中”。主工单不进入补录节点，审核退回处理阶段时回到“处理中”；主单筛选字典只读取主单状态机，子单筛选字典只读取子单状态机。

工单池约定：工单处理和子单处理的“待处理”表示尚未被处理员领取，只出现在机构工单池；点击“处理”会同时领取并进入个人工作台。下辖工单池展示处理至审批阶段的非办结单据，仅提供催办和查看。审批管理按角色区分：复核员工作台/机构池仅展示待复核、复核中且下辖池为空；审批员工作台展示会签中、待审批、审批中，机构池/下辖池展示待处理、处理中、待审批、审批中，下辖池按状态提供查看、转派和催办。溯源整改操作栏不提供催办。

关联子流程统一由子单记录生成，不维护重复的“关联子流程信息”字段区块：工单处理页只保留“关联子流程”列表，草稿和已废止子单不进入列表；进入流转或已办结且已有编号的子单才展示。申请状态直接使用子单状态，结论回显子单同名结论字段；工单详情“关联子流程”和“关联单据”必须使用同一数据集合。工单处理、子单创建和子单处理不展示“已办结”记录；工单创建原则上仅展示未办结记录，但保留一条标记为客服系统带入的已办结投诉单，用于只读演示完整流程和详情；查询导出保留全部状态。

导出申请状态机为“草稿 → 待审批 → 审批中 → 已通过/已驳回”，导出类型统一为“工单、子单、溯源整改单、报表”。查询导出中的“导出”先选择“是否脱敏”：脱敏导出直接生成导出台账记录；非脱敏导出必须勾选敏感字段并提交审批，通过后在“导出申请”中下载。导出台账作为查询导出的第四个栏目，记录所有实际导出操作。

### 子流程字段与状态维护

最新版业务字段以项目外部评审表“子流程单字段表.xlsx”为业务输入，落地后的唯一代码源仍是 [data/forms/subprocesses.json](data/forms/subprocesses.json)。不要让页面直接读取 Excel，也不要直接修改生成文件。字段配置按以下边界维护：

| 配置位置 | 负责内容 |
| --- | --- |
| `base_field_rules.common_fields` | 所有子单共有的创建人、机构、编号、申请时间和处置期限 |
| `base_field_rules.type_fields` | 异常投诉、剔除申请等类型专属基础字段 |
| `field_sections` | 创建阶段和处理阶段的业务字段 |
| `process_section_titles` | 哪些分区在处理阶段编辑 |
| `approval_rules` | 初审、终审、免审批和补录类型 |
| `supplement_sections` | 延长申请、异常投诉、剔除申请的补录字段 |

子流程状态总顺序为：`草稿 → 待提交 → 待复核 → 复核中 → 待处理 → 处理中 → 待初审 → 初审中 → 待审批 → 审批中 → 待补录 → 已办结/已废止`。不是每种子流程都会经过全部状态，实际适用节点由 [data/workflow-schema.json](data/workflow-schema.json) 的 `documentStateMachines.subprocess.typeStatusMatrix` 控制。

| 子流程类型 | 实际流转路径 |
| --- | --- |
| 撤销投诉 | 草稿 →（客服渠道：待复核 → 复核中）→ 已办结 |
| 废止申请 | 草稿 →（客服渠道：待复核 → 复核中）→ 待初审 → 初审中 → 待审批 → 审批中 → 已办结 |
| 投诉校正 | 草稿 →（客服渠道：待复核 → 复核中）→ 待审批 → 审批中 → 已办结 |
| 异常投诉、剔除申请 | 草稿 → 待处理 → 处理中 → 待初审 → 初审中 → 待审批 → 审批中 → 待补录 → 已办结 |
| 延长申请 | 草稿 →（满足初审条件：待初审 → 初审中）→ 待审批 → 审批中 → 待补录 → 已办结 |
| 纠纷化解 | 草稿 → 待审批 → 审批中 → 已办结 |
| 投诉调查、异议核查 | 草稿 → 待处理 → 处理中 → 待初审 → 初审中 → 待审批 → 审批中 → 已办结 |
| 投诉问责（人工触发） | 草稿 → 待审批 → 审批中 → 已办结 |
| 投诉问责（系统自动触发） | 待处理 → 处理中 → 待审批 → 审批中 → 已办结 |

“客服渠道”当前指关联主工单受理渠道为“客服电话”或“在线客服”。子流程复核、初审和审批表单显示在可提交业务内容的最后：有处理阶段的子单放在“处理信息”末尾；无处理阶段的子单不显示“处理信息”页签，审批表单放在“基本信息”末尾。修改字段或状态后至少运行 `npm run build`、`npm run test:subprocess-contract`、`npm run test:supplement` 和 `npm run verify`。

主工单、子流程的流转记录数据契约由 [data/workflow-schema.json](data/workflow-schema.json) 的 `workflowRecordSchema` 维护，页面固定按“操作人、角色、机构、流转场景、流转意见、接收对象、状态流转、操作时间”展示。记录在操作成功后生成，保存人员、角色和机构快照；状态流转始终显示“原状态 → 新状态”，操作时间精确到秒，空值统一显示“-”。

当前浏览器演示数据版本为 `storageVersion: 24`。首次打开新版本时旧的本地演示操作会重置为最新样例，这是原型的数据迁移策略，不影响仓库源文件。

## 九、前后端对接边界

当前所有业务数据都是前端 Mock。准备接真实后端时不要直接在页面里散写 `fetch()`，推荐按以下顺序：

1. 先为模块定义 repository/service 接口。
2. 保留现有 Mock 实现，保证原型仍可离线演示。
3. 新增 API 实现，通过配置选择 Mock 或 API。
4. 为请求、响应和错误状态定义可验证的 schema。
5. 明确登录、权限、文件上传、审计、分页和并发规则。
6. 前后端基于同一份接口契约联调。

生产系统不能复用当前前端权限判断作为安全控制，也不能使用本仓库中的假数据结构替代正式数据治理。

## 十、Netlify 部署说明

仓库已连接 Netlify 项目 `trsxib`，生产分支为 `main`，正式地址为 <https://trsxib.netlify.app/>。协作者只在功能分支开发并提交 PR；由仓库负责人审核并合并到 `main` 后，Netlify 自动创建 Production Deploy 并更新正式原型。功能分支不会影响正式地址。

合并前应确认 GitHub `verify` 通过；合并后由仓库负责人在 Netlify 项目的 Deploys 页面确认对应 `main` 提交状态为 `Published`，并检查正式地址。Production Deploy 失败时暂停后续合并，优先修复部署。

Netlify 只负责部署 `main`，协作者不需要 Netlify 项目权限。仓库负责人统一负责合并和生产部署验收。

## 十二、当前限制

- 无真实登录、数据库、后端接口、文件服务或 Excel 解析服务。
- 客户查询、AI 打标、风险提示、导出和审批均为演示逻辑。

- 业务字段、流程和审批规则仍会随业务确认继续调整。


### 会签与关联子流程数据维护

- 工单处理联系记录：处理部门只展示部门名称，去掉总行或分行前缀；需审批短信的审批状态为“待审批 / 已通过 / 已驳回”，无需审批或非短信记录显示“-”。联系状态为“已联系 / 未送达 / 未接通 / -”；待审批或已驳回的短信不显示“已联系”。沟通方式覆盖一键外呼、短信沟通、邮件、面访、微信、电话、短信和其它。开发测试视图提供上述状态与方式的演示记录，每页展示 5 条；状态标签只使用两种颜色。驳回后可编辑，审批通过但未送达时可重发；重发后联系状态保持空值，待送达结果回传。
- 异常风险识别：当前逐笔风险标签为原型演示数据，不依据录音内容生成，页面会明确提示；普通视图展示全部已回传的一键外呼记录，开发测试视图仅展示三笔样例。
- 会签配置：主工单处理页的“会签信息”独立于“处理结果”。“会签机构”复用机构树数据，支持多选并显示完整机构前缀；审批管理中的“会签意见”按会签人逐行展示。工单在全部会签人完成前保持“会签中”，全部完成后进入“待审批”，审批人领取后变为“审批中”。
- 多人会签样例：保存在 `data/seed-data.json` 的 `documentData.tickets.<工单编号>.fields.countersign.会签明细`。每行维护会签机构、会签人、会签状态、会签结论和会签意见。
- 关联子流程：每个子单单独占一行；同一类型有多个子单时仅合并“子流程类型”单元格。结论统一展示为“字段名称 - 字段值”，操作栏只保留“发起”和“详情”。
- 关联关系：子单列表的 `relatedTicketId`、子单详情的 `relatedTicketIds` 与“关联工单编号”必须同步修改。多个关联工单编号在列表中显示为“首个编号/...”，点击后用宽弹窗展示全部可跳转编号。运行 `npm run verify` 会校验关联完整性。
- 子单抄送：所有子单详情的基本信息末尾固定展示只读“抄送人”。撤销投诉取关联主单处理员，投诉校正取关联主单经办员，30 日延长申请取总行消保部主管审批员；创建子单时按结构化关联关系计算并保存。


### 子流程补录

- 延长申请、异常投诉、剔除申请审批通过后进入“待补录”。补录入口打开子单详情的“处理信息”，原创建与处理字段全部只读，补录分区固定在页面最后。
- 延长申请补录“是否告知延期、告知延期时间、告知延期方式”。选择联系记录后，时间和方式由系统自动回填，不允许手工修改。
- 异常投诉补录“异常认定结果”，取值为“认定成功、认定失败”；剔除申请补录“剔除认定结果”，取值为“剔除成功、剔除失败”。
- 补录字段源位于 `data/forms/subprocesses.json` 的 `supplement_sections`，提交值保存在子单 `fields.supplement`。
